# Relationship Model

> **Status:** `contains`, `imports`, `exports`, `reExports` are **implemented** in Phase 1. Every
> other relationship kind named in this document (`calls`, `constructs`, `extends`, `implements`,
> `reads`, `writes`, and others) is **not implemented** — named here only to show where Phase 1's
> boundary sits relative to the long-term design.

## The implemented kind set

```ts
export type RelationshipKind = "contains" | "imports" | "exports" | "reExports";

export interface SemanticRelationship {
  id: string;
  sourceId: string;
  targetId?: string; // absent when the target could not be cheaply resolved
  candidateTargetIds?: string[]; // reserved for future dynamic-dispatch cases; unused in Phase 1
  kind: RelationshipKind;
  location?: SourceLocation;
  confidence: number;
  evidenceIds: string[];
}
```

This is deliberately narrower than the full long-term relationship vocabulary
(`calls`, `constructs`, `extends`, `implements`, `reads`, `writes`, `returns`, `throws`,
`dependsOn`, `exposes`, and others named in the product spec). Those all require either
symbol-resolved binding (which kind of thing does this identifier refer to?) or control-flow
analysis (what does this branch actually do?) — both explicitly out of scope for Phase 1. Phase 1
only implements the relationships that can be derived cheaply and reliably from syntax and
project-relative path resolution alone.

### `contains`

Structural containment: file → top-level entity, class/interface → member, variable → the nested
function/arrow expression it holds. `sourceId` is the parent's entity id, `targetId` is the child's
— always resolved, since both ends were just constructed together during the same AST walk. This
relationship duplicates what `entity.parentId` already tells you; it exists as an explicit graph
edge for consumers who prefer traversing relationships uniformly rather than switching between
`parentId` lookups and relationship edges.

### `imports`

Module → module, one relationship per `import ... from "specifier"` (or `import "specifier"`) in a
file. `sourceId` is always the importing module's entity id (its project-relative path). `targetId`
is the imported module's entity id, **if and only if** the specifier could be cheaply resolved —
see [Resolved vs. unresolved targets](#resolved-vs-unresolved-targets) below.

### `exports`

Module → entity. Derived from three source shapes:

- A declaration with an `export` modifier directly on it (`export class Foo`, `export function
foo() {}`, `export const x = ...`).
- A same-file named export list without a `from` clause (`export { foo, bar as baz }`) — resolved
  against the file's own top-level entities by name.
- `export default <expression>` — recorded, but `targetId` is only set when the exported name can
  be matched to a local entity; an inline expression (`export default { ... }`) has no name to
  match, so `targetId` stays `undefined`.

### `reExports`

Module → module, derived from `export { x } from "specifier"` and `export * from "specifier"`.
Resolved the same way as `imports` (see below), one relationship per named element for a named
re-export list, or a single relationship for `export * from ...`.

## Resolved vs. unresolved targets

Every `imports`/`reExports` relationship's specifier is resolved by
`src/language/typescript/resolve-module-relationships.ts`, **after** every file in the project has
been parsed and its entities are known (this is why relationship resolution is a distinct pass from
entity extraction — it needs the full file inventory, not just one file's AST).

Resolution only attempts relative specifiers (those starting with `.`):

1. The specifier is joined against the importing file's directory and normalized to a
   project-relative POSIX path.
2. Candidate paths are generated by appending each of `.ts`, `.tsx`, `.d.ts`, `.js`, `.jsx`,
   `.mjs`, `.cjs`, and by trying `index` + each of those extensions inside the resulting directory.
3. **`.js`-style specifiers pointing at TypeScript source:** TypeScript-authored ESM code
   conventionally imports the _compiled_ extension even though the source is TypeScript — for
   example `import { x } from "./wallet.js"` when the actual file is `wallet.ts`. Codara
   recognizes this convention explicitly: a specifier ending in `.js`/`.jsx`/`.mjs`/`.cjs` also
   tries the corresponding source extension(s) (`.js`→`.ts`/`.tsx`, `.jsx`→`.tsx`, `.mjs`→`.mts`,
   `.cjs`→`.cts`) before giving up.
4. The first candidate that matches a file already present in the project's file inventory becomes
   `targetId`.

If none of the candidates match — or the specifier is not relative at all (a bare package name like
`"react"`, or a `tsconfig` path alias like `"@lib/format"`) — `targetId` is left `undefined`.
**Codara never fabricates a guessed target.** This is a deliberate choice: a wrong relationship is
worse than a missing one, because a wrong relationship looks exactly as confident as a correct one
to a downstream consumer unless confidence is tracked — which brings us to:

## Confidence

Every relationship in Phase 1 has `confidence: 1` **except** unresolved `imports`/`exports`/
`reExports`, which get `confidence: 0.6`. This is not a graded scale calibrated against real-world
accuracy — it is a binary signal: "this target was actually resolved" (`1`) versus "this target is
asserted to exist based on the specifier/name alone, but could not be located in this project's
file inventory" (`0.6`). A consumer that only trusts `confidence === 1` relationships will never
see a fabricated edge.

## Evidence

Every relationship carries at least one `evidenceIds` entry. `contains` relationships are backed by
a `sourceRange` evidence record; `imports`/`exports`/`reExports` are backed by an `importBinding`
evidence record whose `explanation` states in plain language whether the target was resolved and,
if not, that it's likely an external package or an alias. See
[06-evidence-and-confidence.md](06-evidence-and-confidence.md) for the full evidence model.

## Why path aliases and bare specifiers remain unresolved in Phase 1

Resolving a `tsconfig.json` `paths` alias (e.g. `"@lib/*": ["src/lib/*"]`) or a bare package
specifier (`"react"`, `"lodash/debounce"`) correctly requires the same module-resolution logic the
TypeScript compiler itself uses internally — which in turn depends on `node_modules` layout,
package `exports` maps, and potentially multiple candidate resolution strategies. Phase 1's
resolver is intentionally a simple, dependency-free, relative-path-only matcher against the
project's own file inventory (see above) — it does not re-implement Node/TypeScript module
resolution. Recording these specifiers as unresolved, with reduced confidence, is consistent with
the project's broader stance: a relationship Codara cannot cheaply and reliably establish is
reported as absent rather than guessed.

## Planned relationship categories (not implemented)

These require symbol resolution and/or control-flow analysis Phase 1 explicitly does not perform.
They are listed here only so the boundary is visible, not as a roadmap commitment:

| Kind                 | Would require                                                                       |
| -------------------- | ----------------------------------------------------------------------------------- |
| `calls`              | Resolving a call expression's callee to the function/method it invokes              |
| `constructs`         | Resolving a `new` expression's target to a class declaration                        |
| `extends`            | Resolving a class/interface heritage clause to its base declaration                 |
| `implements`         | Resolving an implements clause to the interface(s) it satisfies                     |
| `reads` / `writes`   | Data-flow analysis of which entity reads or mutates which state                     |
| `returns` / `throws` | Local control-flow decomposition — see [05-behavior-model.md](05-behavior-model.md) |
| `dependsOn`          | A synthesized, higher-level view over `calls`/`constructs`/`imports`                |
| `exposes`            | Entry-point and side-effect recognition at the project boundary                     |

None of these appear in `RelationshipKind` today, and no code path produces them. Adding one is a
schema-additive change (a new union member), not a redesign of the relationship shape itself.
